Análise do RabbitMQ no Domus

  1. O Problema que o RabbitMQ Resolve Aqui

  O usuário faz upload de um extrato bancário (CSV/OFX/PDF). Processar isso é lento — envolve:
  1. Salvar o arquivo no banco
  2. Chamar um microserviço Python para parsear o arquivo
  3. Salvar dezenas de transações no PostgreSQL

  Se isso fosse síncrono, a requisição HTTP ficaria pendurada por 5-30 segundos. O RabbitMQ resolve isso transformando o
   processamento em assíncrono: o usuário recebe uma resposta imediata (202 Accepted + um jobId), e o processamento
  pesado acontece em background.

  2. A Arquitetura Completa (do início ao fim)

  FRONTEND
      │
      │ POST /api/statement/import (arquivo + dueDate)
      ▼
  StatementController.importStatement()
      │
      ▼
  StatementService.enqueueImport()
      ├── 1. Salva arquivo no banco (tabela import_jobs, status=PENDING)
      ├── 2. Registra afterCommit hook
      └── 3. Retorna jobId imediatamente → 202 Accepted

      [após o commit da transação]
      │
      ▼
  StatementImportProducer.sendImportJob(jobId)
      │
      │ RabbitMQ: exchange=domus.statement.direct
      │           routingKey=statement.import
      │           mensagem={ jobId }
      ▼
      [fila: domus.statement.import]
      │
      ▼
  StatementImportConsumer.handleImportMessage()
      ├── Tx1: markJobProcessing()  → status=PROCESSING
      ├── Tx2: doProcessImportJob() → chama Python, salva outgoings, status=DONE
      └── Tx3: markJobError()       → status=ERROR (só se Tx2 falhou)

  FRONTEND (polling)
      │
      │ GET /api/statement/status/{jobId}
      ▼
  StatementService.getJobStatus()
      └── retorna: PENDING | PROCESSING | DONE | ERROR

  3. As Decisões Técnicas Importantes (e por que existem)

  Decisão 1: Direct Exchange ao invés de publicar direto na fila

  O que está no código (RabbitMQConfig.java:47-52):
  BindingBuilder.bind(importQueue)
      .to(importExchange)
      .with(IMPORT_ROUTING_KEY);

  Por que isso importa: O producer (StatementImportProducer) só conhece o exchange e a routing key, não sabe qual fila
  existe. Isso desacopla quem publica de quem consome. No futuro, você pode adicionar uma segunda fila (ex: para
  auditoria) no mesmo exchange sem mudar o producer.

  ---
  Decisão 2: A mensagem carrega só o jobId, não o arquivo

  O que está no código (StatementImportMessage.java):
  public class StatementImportMessage {
      private String jobId;
  }

  Por que isso importa: O arquivo pode ter megabytes. Mensagens RabbitMQ trafegam pela rede e têm limite de tamanho. O
  arquivo fica no banco (import_jobs.file_bytes), e o consumer busca pelos bytes usando o jobId. Mensagem pequena =
  broker rápido e estável.

  ---
  Decisão 3: Publicar no RabbitMQ APÓS o commit (afterCommit)

  O que está no código (StatementService.java:85-89):
  TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
      @Override
      public void afterCommit() {
          statementImportProducer.sendImportJob(jobId);
      }
  });

  Por que isso importa: Se o sendImportJob fosse chamado dentro da transação, o consumer poderia receber a mensagem e
  tentar buscar o job no banco antes do commit — e não encontraria nada (race condition). O afterCommit garante que o
  job já está persistido quando o consumer acorda.

  ---
  Decisão 4: 3 transações separadas no consumer

  O que está no código (StatementImportConsumer.java:46-62):
  // Tx1 — curta
  statementService.markJobProcessing(jobId);

  // Tx2 — principal (pode ser lenta)
  statementService.doProcessImportJob(jobId);

  // Tx3 — registra o erro se Tx2 falhou
  statementService.markJobError(jobId, e.getMessage());

  Por que isso importa: Se tudo fosse uma única @Transactional, a conexão do pool ficaria aberta durante a chamada HTTP
  ao Python (que pode levar segundos). Além disso, se Tx2 falhasse, o rollback reverteria até o status PROCESSING, e o
  catch não conseguiria persistir ERROR (a transação já estaria marcada para rollback). Separar em 3 transações curtas
  resolve os dois problemas.

  ---
  Decisão 5: Filas e exchanges duráveis

  O que está no código (RabbitMQConfig.java:37-43):
  return QueueBuilder.durable(IMPORT_QUEUE).build();
  return ExchangeBuilder.directExchange(IMPORT_EXCHANGE).durable(true).build();

  Por que isso importa: Se o RabbitMQ reiniciar (deploy, crash), filas e exchanges não somem. Mensagens que estavam na
  fila sobrevivem ao restart.

  5. Como Falar Disso com Confiança na Entrevista

  Script de abertura (responda assim quando perguntarem "o que você usou?")

  ▎ "Implementei um fluxo assíncrono de importação de extratos bancários usando RabbitMQ com Spring AMQP. O usuário faz
  ▎ upload de um arquivo, o Java salva no banco, publica um jobId no RabbitMQ e retorna 202 imediatamente. Um consumer
  ▎ processa em background: chama um microserviço Python para parsear o arquivo, salva as transações, e atualiza o
  ▎ status do job. O frontend faz polling no endpoint de status para saber quando terminou."

  ---
  Perguntas que vão vir — e como responder

  "Por que RabbitMQ e não processar direto?"

  ▎ "Porque o processamento é lento — envolve uma chamada HTTP para um microserviço Python e vários inserts no banco.
  ▎ Processar de forma síncrona deixaria o usuário esperando. Com o RabbitMQ, a resposta é imediata e o processamento
  ▎ acontece em background."

  "Por que você usa Direct Exchange ao invés de publicar direto na fila?"

  ▎ "Para desacoplar o producer da fila. O producer só conhece o exchange e a routing key. Se amanhã eu quiser adicionar
  ▎  uma segunda fila — por exemplo para auditoria — não preciso mudar nada no producer, só adiciono um novo binding."

  "Por que a mensagem carrega só o jobId e não o arquivo?"

  ▎ "Porque mensagens RabbitMQ trafegam pela rede e têm limite de tamanho. O arquivo pode ter megabytes. Guardo os bytes
  ▎  no banco e o consumer busca por eles usando o jobId. Mensagem pequena, broker rápido."

  "Por que você publica no RabbitMQ depois do commit e não dentro da transação?"

  ▎ "Para evitar race condition. Se eu publicasse dentro da transação, o consumer poderia acordar antes do commit e
  ▎ tentar buscar o job no banco — e não encontraria nada, porque o registro ainda não foi commitado. Usando afterCommit
  ▎  do Spring, garanto que o job já está no banco antes de qualquer consumer receber a mensagem."

  "Por que 3 transações separadas no consumer?"

  ▎ "Por dois motivos. Primeiro: se a transação principal ficasse aberta durante a chamada HTTP ao Python, estaria
  ▎ segurando uma conexão do pool por vários segundos desnecessariamente. Segundo: se eu tivesse tudo em uma única
  ▎ @Transactional e ela falhasse, o rollback reverteria o status para PROCESSING, e o bloco catch não conseguiria
  ▎ persistir o status ERROR porque a transação já estaria marcada para rollback."

  6. O que está bom no código (fale isso com propriedade)

  - Idempotência: existe um importHash (MD5 de user+data+descrição+valor) para evitar duplicatas na importação. Se a
  mesma transação aparecer duas vezes no extrato, ela é ignorada.
  - Separação de responsabilidades: Producer, Consumer e Service são classes distintas. O Consumer só orquestra, a
  lógica de negócio fica no Service.
  - Segurança no polling: getJobStatus valida que o jobId pertence ao usuário autenticado.
  - Infraestrutura correta: o docker-compose usa depends_on com condition: service_healthy para garantir que o Java só
  sobe depois que o RabbitMQ e o PostgreSQL estão prontos.

  ---
  7. O que você pode melhorar (mostre maturidade citando isso)

  Isso impressiona em entrevistas — admitir limitações demonstra que você pensa além do que está implementado:

  - Mensagens não são persistentes (message durability): as filas são duráveis, mas as mensagens não foram marcadas como
   persistentes explicitamente (deliveryMode=PERSISTENT). Se o broker cair com mensagens na fila mas não commitadas,
  elas se perdem. Solução: rabbitTemplate.setMandatory(true) + MessageProperties.PERSISTENT_TEXT_PLAIN.
  - Sem Dead Letter Queue (DLQ): se o consumer falhar repetidamente, a mensagem é descartada. Uma DLQ capturaria essas
  mensagens para análise posterior.
  - Polling é ineficiente em escala: o frontend faz polling para saber o status. Para escalar, o ideal seria WebSocket
  ou SSE (Server-Sent Events) para o Java notificar o frontend quando o job terminar.
  - Arquivo salvo como bytea no PostgreSQL: funciona, mas para arquivos grandes ou alto volume, o correto seria usar S3
  e guardar só a URL no banco.

  ---
  Resumo: Você implementou um padrão clássico de processamento assíncrono com filas — Producer/Consumer + Job Status
  Polling — com várias decisões técnicas não-triviais documentadas no código. Para uma vaga junior, saber explicar o
  afterCommit e as 3 transações separadas já te coloca em uma categoria acima da média.
